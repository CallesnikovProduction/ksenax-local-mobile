# Agentic work

## Назначение

`communication.work` выполняет один независимый Agentic-запрос. Модельные
сессии принадлежат `communication.model`, Android-действия — `tools/builtin`.

```text
UP -> FunctionGemma native selection
   -> fast: известный код -> FG аргументы (если нужны) -> schema/domain -> policy -> executor
   -> planned: G4 JSON plan -> preflight всех входов и FG calls -> policy -> executors по порядку
   -> clarification / unsupported: существующий результат turn, без side effects
```

## Инварианты

- FunctionGemma — единственный модельный выход к executor-у.
- Keywords не участвуют в runtime-маршрутизации. `supportsFastPath` публикует
  функции kit-а в семантическом каталоге; их выбирает FG.
- G4 видит кодовые имена и входные контракты, но не Android-реализации.
- Первый FG-вызов использует короткий каталог функций без аргументов и обычный
  function-calling system prompt. Native constrained decoding ограничивает формат,
  но не правильность выбора. Несколько вызовов отклоняются без исполнения.
  Только параметризованная функция
  получает второй FG-вызов со своей схемой. Так не раздувается контекст 1024.
- В параметризованный FG-запрос передаются UP и явно извлечённые параметры,
  а не служебный текст Local now. Сырой ответ FG всё равно проверяется до merge.
- При противоречии явному UP допускается один повторный FG-выбор внутри уже
  выбранного моделью kit. Локальное ожидаемое имя не заменяет ответ модели;
  повторное противоречие останавливает действие без исполнения.
- Минимальный G4-шаг содержит `action` и `input` в одном объекте; id и instruction
  могут быть вычислены parser-ом, комментарии остаются необязательными метаданными.
- Parser допускает одну точную `json`-оболочку Markdown, но не пояснения, несколько
  корней или исправление JSON. Заполнитель вместо тела заметки отклоняется.
- UP больше 256 UTF-8 байт направляется FG-функцией `route_planned_work` в G4;
  исходный текст не обрезается и не исполняется по одному фрагменту.
- Каждый шаг плана содержит одну FunctionGemma declaration. Native functions
  используют `askFunctions`, не ручной chat-template и не automatic tool calling.
- Аргументы G4 или локального нормализатора передаются executor-у отдельно от
  короткого FunctionGemma prompt, если kit отключил их публикацию.
- Шаги выполняются по порядку; первая ошибка, блокировка или подтверждение
  останавливает план.
- Все входы и ответы FG проверяются до первого executor. Hardware-операции не
  транзакционны: ошибку позднего исполнения нельзя откатить автоматически.
- `validatePlannedInputs` сверяет весь набор шагов kit-а с исходными командами
  до FG-компиляции: число и порядок команд внутри kit, количество будильников,
  единицы, дату, время и явно указанную продолжительность события в минутах.
  Потерянный/повторённый шаг или неоднозначность требуют уточнения, не исправления
  предложения G4. Генерируемое содержание заметки этой проверкой не оценивается.
- Kit проверяет основание аппаратного действия в исходном UP и для fast, и для
  planned. Цитата или обсуждение инструмента не являются таким основанием.
  Эта проверка может запретить выбор модели, но никогда не выбирает tool сама.
- Утверждение о состоянии не разрешает действие. Потребность привязывается к
  объекту kit-а; перед ним допустимо только проверенное числительное, не чужой
  предмет. Краткое «будильник на HH:mm» сохраняется как отдельная форма команды.
- `validateSourceCall` дополнительно проверяет конкретное действие для обоих
  маршрутов: направление фонарика и отдельное разрешение массового отключения
  будильников. Обычная команда постановки не разрешает `alarm_clear_all`.
  Проверка сохраняет границы команд: глагол фонарика нельзя заимствовать для
  будильников и наоборот.
- Относительная дата закрепляется до первого inference. Проверка того, что
  событие ещё не истекло, использует актуальное время перед исполнением.
- Неясные числа/время означают уточнение. Составной интервал пока уточняется,
  не сокращается до первой величины. Clock ограничен ближайшими 24 часами.
- Календарь использует canonical local datetime; delay/all_day не входят в этот
  атомарный контракт. Экран сохранения события по-прежнему принадлежит Android.
- Проверка исходного разрешения обязательна в контракте каждого kit. Запись и
  анализ заметки требуют своей команды в UP; обсуждение или открытие заметки
  не разрешают её создание. Заметка требует типизированного текста G4;
  отсутствующий текст не заменяется UP.
- После выбора FG допуск проверяется до загрузки G4: если ни один kit не
  разрешает исходный запрос, возвращается уточнение без планирования. Эта
  проверка не выбирает kit и не заменяет ошибочный выбор FG локальным действием.
- Каждый разрешённый kit проверяет `validatePlanningSource` до загрузки G4.
  Alarm/Calendar используют те же ограничения явных значений, что и post-plan
  проверка. Неполная команда останавливает весь mixed-запрос без частичного
  действия; проверка не создаёт шаги и не требует будущий текст заметки.
- Mutex сериализует turns одного runtime. Отмена пробрасывается, а diagnostic
  events содержат только стадию, имя функции, latency и категорию ошибки.
- Agentic-turn не использует persistent conversation.

## Папки

### Проверка Qwen (SPEC-001B)

Под SPEC-001B тестируется Qwen3-0.6B, не FG. `QwenRoutingProtocol` задаёт
отдельный JSON-контракт четырёх маршрутов: system содержит каталог и правила,
user — только UP. `KsenaxRoutingDecision` не авторизует действие. Native Qwen
использует ChatML и JSON в `<tool_call>`, а не синтаксис FunctionGemma.
Протокол пока не включён в рабочий runtime: focused live-gate не пройден.
Существующий FG-путь выше описывает установленную версию, не замену Qwen в тесте.
Policy, schemas и Android-executors не зависят от выбранной модели.
Legacy dynamic INT8 файл Qwen имеет basic-template и Generic processor:
его metadata не задаёт Qwen3 type/Jinja/channels. Для live-тестов используется
официальный Qwen Jinja SDK 0.13.1; raw Hermes `<tool_call>` проверяется
`parseHermesResponse` до DTO, включая повторные ключи. Это не SDK ToolCall
и не repair готового ответа. Рабочий runtime пока не переключён.

- `routing` — семантический выбор функции или планирования/уточнения/отказа;
- `planning` — компактный G4 prompt, DTO и строгий JSON-parser;
- `oneshot` — FunctionGemma template, declarations и parser ответа;
- `actions` — внешний контракт action kit и прямого маршрута;
- `runtime` — порядок моделей, policy и executor-ов;
- `turn` — внешний результат и стадии одного запроса.

Новые публичные типы имеют префикс `Ksenax`, краткий KDoc,
`@author Stephan Kolesnikov` и `@since 0.4`.
