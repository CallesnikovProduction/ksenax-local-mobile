Текущая ветка разработки — **OpenKsenax 0.3**. Версия 0.2 считается
зафиксированным историческим срезом. Любая новая KDoc-документация, публичный

только ради смены версии.

## Позиция OpenKsenax

OpenKsenax (OKx) — не монолитный оркестратор, который должен знать все
пользовательские сценарии. Начиная с версии 0.3 это мобильный контейнер
самостоятельных addon APK.

Каждый аддон является отдельным Android-приложением и сам владеет:

- своей предметной логикой и правилами оркестрации;
- своим UI и пользовательскими настройками;
- foreground/background services;
- разрешениями, процессом и жизненным циклом;
- хранением собственных данных и обработкой событий своего сценария.

OKx предоставляет общую платформу: каталог опубликованных аддонов, обнаружение
установленных APK, проверку совместимости и доверия, системные команды
установки/удаления/открытия и контролируемый IPC-доступ к локальным моделям.
Аддон может использовать доменную модель ИИ из OKx, но OKx не исполняет за него
предметную логику и не рисует его рабочий интерфейс.

## Ментальная модель addon-платформы

Основной поток выглядит так:

1. `catalog` сообщает, какие аддоны опубликованы и какой identity ожидается;
2. `discovery` независимо находит addon APK через Android `PackageManager`;
3. `registry` объединяет оба источника с возможностями текущего host и один раз
   вычисляет installation, compatibility, trust и разрешённые capabilities;
4. `coordination` выполняет только пользовательские команды над уже
   зарегистрированным аддоном;
5. `modelprovider` авторизует Binder-caller через registry и делегирует
   разрешённый запрос существующему model runtime OKx;
6. UI OKx показывает каталог и управление, а рабочий UI запускается и рисуется
   самим addon APK.

Аддоны не загружаются как writable DEX внутрь процесса OKx и не передают хосту
Compose-классы. Граница между APK должна оставаться явной Android IPC-границей.

## Границы ответственности

OKx отвечает за:

- версионированный addon-контракт и стабильные идентификаторы;
- получение, декодирование и валидацию внешнего registry;
- discovery установленного APK без доверия к его self-declared metadata;
- единый verdict доверия, совместимости и capability grants;
- безопасную передачу APK системному installer с участием пользователя;
- проверку Binder UID/package перед доступом к host capabilities;
- владение и жизненный цикл локального model runtime.

Аддон отвечает за:

- собственный Android Manifest, services, permissions и foreground notification;
- защита exported management service через host signature-permission и
  проверку UID/package/signing certificate вызывающего OKx;
- собственную автоматизацию, policy, таймеры, rule engine и ошибки;
- собственный UI и entry point, передаваемый OKx через публичный контракт;
- корректное использование выданных host capabilities;
- совместимость своего APK с опубликованной версией протокола.

Модель предлагает или генерирует данные, но не получает безусловной власти над
устройством. Android permissions, пользовательское подтверждение и policy
конкретного аддона остаются реальными границами исполнения.

## Архитектурные принципы

- `contract` не зависит от остальных addon-контуров;
- `catalog` и `discovery` независимы друг от друга;
- `registry` — единственное место объединения catalog, discovery и host state;
- `coordination` и `modelprovider` потребляют готовый verdict registry и не
  копируют проверки сертификата, trust или compatibility;
- presentation не работает напрямую с `PackageManager`, HTTP или raw JSON;
- Android `Context` не передаётся в domain-модели;
- внешние идентификаторы представлены типами `AddonId` и `HostCapabilityId`;
- DTO внешнего JSON, domain-модели и UI state не смешиваются;
- сетевой, файловый и PackageManager IO не выполняется на main thread;
- отмена coroutine не превращается в обычную ошибку;
- отсутствие registry, модели или разрешения означает явный fail-closed
  результат, а не фиктивный успех;
- один process-level composition root принадлежит `KsenaxAndroidApplication`;
- отдельный Gradle-модуль создаётся только для настоящей ABI/ownership-границы,
  а не для каждого package.

## Приоритет разработки

Сначала нужно доказать устойчивый узкий контур:

- каталог можно безопасно получить, проверить и закэшировать;
- установленный APK обнаруживается и однозначно сопоставляется с записью;
- сертификат, protocol/API version и capabilities проверяются централизованно;
- OKx открывает принадлежащий аддону UI без знания имени его Activity;
- доверенный аддон получает только явно разрешённую model capability;
- ошибки сети, установки, IPC и model runtime видимы и не маскируются.

Не следует преждевременно добавлять silent install, загрузку произвольного DEX,
встраивание чужого Compose UI, универсальный capability API или cloud-контур.
Расширение допустимо после проверки минимального Android APK + Binder потока.

## Рабочее понимание результата

Успешный OpenKsenax 0.3 — это local-first Android-host, в котором пользователь
сам выбирает и устанавливает необходимые автономные аддоны. Каждый аддон решает
одну предметную задачу в собственном процессе, а OKx предоставляет ему
проверяемую платформенную основу и ограниченный доступ к локальной модели.

NO RADAR является первым реальным потребителем этой архитектуры, но ни один
общий контур OKx не должен содержать специальных условий по его имени, package
или классам.
